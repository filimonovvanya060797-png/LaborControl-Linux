# LaborControl R11 → ALT Linux — полный цикл тестов и приёмки

**21 ноября 2026. Статус: план, не отчёт о прохождении.**
Контекст: один техник на одном ПК ALT Workstation K 11.4 в VirtualBox, две колонны, около 450 водителей. Цель — функциональная эквивалентность Windows R11, а не только сходный экран. Связанные документы: `docs/TEST_MATRIX_R11.md`, `docs/PERFORMANCE_AND_SCALE.md`, `docs/PROJECT_HANDOVER.md`, `docs/reference/README_RU.txt`.

## A. Принципы и остановка испытаний

- **Рабочую базу никогда не использовать для теста.** Для Linux применять отдельный `XDG_DATA_HOME`; для Windows — изолированный тестовый профиль или VM с доказанно отдельной базой. Когда изоляция эталонного Windows R11 не подтверждена, изменяющие тесты на нём запрещены.
- В GitHub/CI передавать только синтетические fixtures, не загружать туда настоящие ФИО, табельные номера, путевые листы, SAP/ИСАТ, рабочие JSON, токены и секреты.
- Эталон — подтверждённое поведение **Windows R11**, а не старой R3/R9. Если документы или версии правил противоречат друг другу, сравнивать безопасный Windows R11 на одинаковых данных и документировать расхождение. В частности, позднее правило R11: простые положительные часы и `1/N` → дневная смена; `2/N` → ночная; `В/ДП/ОТ/0/пусто` → без смены. Исторический документ `TAB2_RULES.md` даёт старое правило для простых часов.
- **Отдельная «разукрашка»** не считается уже готовой частью исходного R11 Core. Её эталон — действующий Windows Excel-инструмент с согласованной логикой; перенос и приёмка — отдельные обязательные испытания.
- Зелёный GitHub CI или HTTP 200 проверяет только протестированные сценарии, не подтверждает правильность расчётов.
- Для каждого прогона хранить: ID, commit и binary checksum, ОС/Go/браузер, fixture ID/seed, вход, ожидаемый и фактический результат, PASS/FAIL/BLOCKED, безопасный лог/скрин, issue, повторный прогон. Никогда не переносить PASS старого бинарника на новый без теста.

**Критичность:** P0 — потеря данных, изменение чужого сотрудника, неправильные часы/закрытие без предупреждения, доступ к рабочей базе; P1 — ошибка цикла/секции/импорта/редакций/РВД, блокирующая работу; P2 — существенный UX/скорость; P3 — косметика. P0/P1 блокируют приёмку. Ошибки исправляются с обязательным регрессионным тестом.

**Статусы:** `NOT_RUN`, `PASS_UBUNTU`, `PASS_ALT`, `MATCH_WINDOWS`, `FAIL`, `BLOCKED`, `N/A` (с обоснованием). Для бизнес-паритета нужен `MATCH_WINDOWS`, а не только `PASS_UBUNTU`.

## D. Ближайший ручной прогон — компактно

На **уже установленной экспериментальной** версии в отдельной тестовой папке:
1. Зафиксировать commit/version и проверить путь тестовой базы (не импортировать реальные данные).
2. Две вымышленные карточки в разных колоннах, поиск/сохранение/F5.
3. План `1/8 → 1/10` у одного сотрудника; второй и факт неизменны.
4. Два искусственных цикла одного пункта, по одному на вид графика; если Windows-golden ещё не получен, результат `BLOCKED`, не `PASS`.
5. Создать техническую версию → изменить план → восстановить → проверить другого сотрудника.
6. Открыть «Проверку табеля», убедиться в четырёх вкладках и плане из АвтоГрафа; фактические импорты пока только из F04.
7. Штатно завершить/запустить; проверить сохранность синтетических данных и наличие backup.

Нагрузку 450, повреждения файла, production-данные и окончательное закрытие не смешивать с первым ручным прогоном. P0 — немедленно прекратить проверку.

## E. Финальная приёмка и что известно на 21.11.2026

**Приёмка только если:**
1. G0…G5 прошли без открытых P0/P1.
2. Критичные даты/часы/план/факт/сменность/РВД/редакции совпали с Windows R11.
3. «Разукрашка» отдельно сверена с работающим Windows Excel-инструментом.
4. Две колонны/450 водителей проходят полный месяц; проведён нагрузочный сценарий с историей, проверены backup и аварийное восстановление.
