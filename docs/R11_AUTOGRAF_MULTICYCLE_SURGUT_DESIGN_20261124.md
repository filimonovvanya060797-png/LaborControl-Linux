# АвтоГраф R11 — несколько независимых циклов полётов для одного пункта сбора

**Дата уточнения:** 24.11.2026  
**Источник:** прямое пояснение пользователя и реальный ALT-скриншот `Снимок экрана_20261124_021422.png` (PNG приложен к беседе, в GitHub не загружен).  
**Статус:** согласуемая архитектура, **НЕ реализована в программе**, **НЕ приёмка**.

## 1. Исправление ранее неверного понимания

Раньше предполагалось, что `Сург-Тал-Сург 7` и `Сург-Тал-Сург 16` могут являться парой, поэтому в issue #31 / draft PR #32 введён выбор произвольного парного имени. **Пользователь прояснил фактический кейс:** 7 и 16 — **два разных независимых цикла полётов**, которые относятся к одному пункту сбора «Сургут», а **не пары друг другу**. Каждый цикл должен породить СВОЮ пару графиков:

| Цикл | Две опорные ДП (с экрана) | Количество ДП в 2026 по экрану | Пара видов графиков |
| --- | --- | --- | --- |
| Сургут, первый цикл (№7) | 07.01.2026 / 29.01.2026 | 14 | `Сург-Тал-Сург 7` (рабочая первая последовательность), `Сург-Тал-Сург 7.` (свободная) |
| Сургут, второй цикл (№16) | 16.01.2026 / 13.02.2026 | 13 | `Сург-Тал-Сург 16` (рабочая первая последовательность), `Сург-Тал-Сург 16.` (свободная) |

Фазы «Рабочая» у варианта без точки и «Свободная» у варианта с точкой приведены **как предложенная настройка/пример**, а не как независимо подтверждённый норматив для реальных сургутских водителей; пользователь должен утвердить, какой вид начинает с рабочей фазы. Точка остаётся смыслоразличительной для **внутренней пары каждого цикла**. Названия графиков **не являются достаточным идентификатором цикла**: первая ДП или номер могут быть изменены, а год может смениться.

## 2. Почему текущая реализация опасна

Источник `port/controller/r11_original.html`:
- `cycleGroups()` отображает две группы по двум опорным датам, извлекая `Цикл от DD.MM.YYYY / DD.MM.YYYY` из текста `note` каждой `flight_dates`. Этим лишь группируется раздел «Управление построенными циклами».
- `buildByFlights(e,start,end)` в Конструкторе использует:
  `state.data.flight_dates.filter(x=>x.collection_point===e.collection_point&&flightSeq(x))`,
  затем **сортирует вместе все ДП одного пункта сбора**. Он не фильтрует по конкретному циклу, поэтому при сосуществовании двух сургутских циклов может перемешать ДП 7 и 16.
- `scheduleObj(e)` выбирает тип по `schedule_type` и `collection_point`, но у записи вида графика **нет `cycle_id`**.
- `r11FlightSave` на стороне Go при создании записи проверяет уникальность по `collection_point + date`; даты двух циклов, совпавшие в один день, могут не сохраняться как две отдельные сущности.

**Уровень доказательства:** на реальном скриншоте подтверждено **одновременное существование двух разных групп**. По исходному коду подтверждено **отсутствие фильтрации по циклу в Конструкторе**. Пользователь ещё НЕ выполнял и не показывал ошибочный план работы по обоим циклам, поэтому не утверждать, что реальный ALT-план уже был записан неправильно. Это высокий риск логической целостности, приёмку Конструктора для Сургута отложить до исправления.

## 3. UX: работать с циклом, не заполнять дважды форму

В «АвтоГраф → Согласованные полёты → Управление построенными циклами» каждая карточка должна показывать **свою** опорную пару, количество ДП и действие **«Создать/показать виды графиков для этого цикла»**. Пример:

- Цикл №7, Сургут — ДП 07.01 / 29.01, 14 дат → `Сург-Тал-Сург 7` ↔ `Сург-Тал-Сург 7.`
- Цикл №16, Сургут — ДП 16.01 / 13.02, 13 дат → `Сург-Тал-Сург 16` ↔ `Сург-Тал-Сург 16.`

При нажатии кнопки соответствующего цикла программа уже знает **пункт сбора и идентификатор цикла**. Она может предложить основное название, например по дню первой ДП, и показать **предпросмотр двух видов и противоположных фаз**; оператор при необходимости поправляет названия или выбор первой рабочей фазы. **Одно подтверждение** создаёт два вида с привязкой к **этому** циклу. Если пара уже существует, показать связанные виды и «Пара готова» / «Изменить», не делать дубликатов. Переключатель «Другой график» (PR #32) не решает эту задачу и **не должен предлагать 7 ↔ 16 как пару**.

Во вкладке «Виды графиков» показывать отдельную колонку **«Цикл рейсов»** с явным названием/датами, а для новых видов предусмотреть выбор цикла (обязательный, если у пункта их несколько). У сотрудника выбирают вид графика, а нужный цикл определяется автоматически по сохранённой привязке.

## 4. Модель данных и алгоритм (предложение)

1. Стабильная сущность `flight_cycles` (`id`, `collection_point`, `first_anchor`, `second_anchor`, `name/display_label`, `year/period`, метаданные); `id` не меняется из-за переноса ДП.
2. Каждая `flight_dates` хранит `cycle_id`, `date`, `sequence=1|2`; `note` — свободный комментарий/источник, не единственное хранилище связи.
3. Каждый `schedule_types` хранит `cycle_id`, `pair_name` (или устойчивый `pair_id`) и `phase=A|B`. Обе половины пары относятся к **одному и тому же `cycle_id`**.
4. `buildByFlights` выбирает ДП по **`cycle_id` назначенного вида**, а не по одному `collection_point`. Никакие ДП от другого цикла не участвуют в расчёте даже при совпадающем направлении.
5. Повторная запись рейса проверяет уникальность в границах цикла (`cycle_id+date`), а не глобально для пункта; один календарный день может присутствовать в двух разных циклах без перезаписи чужой записи.
6. При удалении цикла с привязанными графиками и сотрудниками требовать ясного предупреждения/блокировки и сохранять историю редакций. Не позволять массовое удаление рабочих данных без однозначного подтверждения.

### Миграция существующих данных — обязательна

- Сперва резервная копия, отдельная миграция с тестом повторного запуска, rollback/журналом; **не удалять** проверенную Тюменскую пару и реестры ДП.
- Для дат, уже имеющих пометку `Цикл от ... / ...`, создать реестр циклов и связать по исходным меткам. Если метки отсутствуют или противоречат — пометить для ручной проверки, не приклеивать к ближайшему циклу.
- Для существующих видов/сотрудников: если у пункта единственный возможный цикл и связь достоверна, предложить миграцию; если их несколько (Сургут), **не угадывать по названию и дате автоматически без проверки**. Дать оператору простой экран сверки.
- Перенос опорных ДП (#28) требует сохранения `cycle_id` и управляемого перепостроения, не перепривязки по новому имени.

## 5. Приёмка и тесты

- Создать два независимых учебных сургутских цикла с опорами **07.01 / 29.01** и **16.01 / 13.02** в 2026; увидеть **14 и 13** дат соответственно, без смешивания.
- Создать из каждого цикла свою пару `7/7.`, `16/16.`. У обеих пар одинаковые `cycle_id` внутри пары, у разных пар — **разные**. Дополнительные самостоятельные циклы одного пункта не влияют на уже созданные.
- Конструктор для сотрудника с `7` показывает **только ДП №7**, а для `16` — **только ДП №16**, при противоположных фазах пар. Не выдавать общий смешанный список.
- Сохранение, удаление/восстановление, совпавшая дата в двух циклах, повторная запись, конфликт и перезапуск — проверка без потери чужого цикла.
- Go API + UI/WebKitGTK автоматические тесты и отдельная ручная ALT-проверка по одному реальному скрину на ключевой этап.
- Обновить русскую инструкцию #16 с двумя карточками циклов и пояснить, что **пара — это два чередующихся графика внутри одного цикла, а не два соседних номера разных циклов**.

**Связанные issues:** #33 (несколько независимых циклов), #31 (прежний UX выбора произвольного имени — не решение данной проблемы), #28 (перенос опорной ДП), #16 (инструкция). Черновик PR #32 может использоваться только для нестандартных имён *внутри одного цикла* после проверки, не считать его исправлением объединения ДП.

**Рекомендация до исправления:** не строить/записывать графики сотрудников Сургута одновременно по двум разным циклам в текущем Конструкторе. Не создавать связь 7 ↔ 16. Тюменскую принятую пару 9↔9. не трогать.


## 6. Согласованное UX-решение: цикл создаёт пару, рейс редактируется отдельно

**Решение пользователя от 24.11.2026:**
- После сохранения независимого цикла полётов **создание пары видов графиков должно быть естественным продолжением этого же действия**, а не отдельной обязательной процедурой «сначала сохрани цикл, перейди в другой раздел, введи два названия, свяжи вручную». Это требование к **основному маршруту UX**. В справочнике «Виды графиков» остаются просмотр/редактирование и специальные ручные случаи, а не второй обязательный шаг.
- После создания человек должен иметь возможность **перенести отдельную согласованную дату рейса**, если возникла корректировка, не удаляя и не пересоздавая целый цикл.
- Ранее подтверждённая ошибка #28 с изменением второй опорной ДП и старой подписью цикла не должна повториться.

### Сценарий 1. Создать цикл и сразу получить два вида

1. Оператор указывает пункт сбора, две опорные ДП, год и нажимает «Рассчитать». Предпросмотр показывает **исключительно собственные** даты цикла.
2. При первом сохранении спросить в том же диалоге **«Создать два вида графика для этого цикла?»**, заранее показывая пару названий и фазы. Основное удобное действие — **«Сохранить цикл и два графика»**; отдельная опция «Только цикл» остаётся, если имена/фазы пока не утверждены. Без принудительного перехода в другой раздел.
3. Подтверждение создаёт сущность `flight_cycles`, её ДП и два `schedule_types` с **общим `cycle_id`** одной атомарной транзакцией. На повторном запуске у цикла отображаются уже привязанные два вида; дубли не создаются, старые назначения сотрудникам не меняются.
4. Для Сургута: цикл 07.01/29.01 создаёт **7 ↔ 7.**; цикл 16.01/13.02 создаёт **16 ↔ 16.**. Название по дню первой опорной ДП — только редактируемое предложение. Вид без точки не обязательно рабочий по нормативу: противоположные фазы показываются явно и выбираются по фактическому расписанию.
5. Предпросмотр и подтверждение **не меняют существующие** `schedule_types`, `flight_dates` и планы без специального подтверждения и проверки совместимости.

### Сценарий 2. Перенос отдельного согласованного полёта

1. Пользователь открывает **карточку конкретного цикла**, выбирает ДП и нажимает «Изменить дату».
2. Форма показывает **«Было» / «Стало»**, пункт сбора, цикл, номер последовательности 1/2, источник/примечание и **сохранённые графики, которые могут зависеть от этой ДП**. Уточняется причина корректировки (чтобы был след в журнале).
3. **Обычный перенос одной ДП не перестраивает другие ДП автоматически.** Программа сохраняет неизменными `cycle_id` и `sequence` перенесённой записи; гарантирует, что дата не перезаписана рейсом другого цикла, и проверяет хронологию, пересечения и совпадения в одном цикле. Соседние рейсы не меняются без явного действия пользователя.
4. **Если это опорная ДП** или перенос меняет логику чередования/периоды, программа до сохранения предупреждает, что может потребоваться пересмотр всего цикла. Предлагает два понятных варианта:
   - **«Перенести только этот рейс»** с последующей проверкой фаз и понятным предупреждением об изменённом интервале;
   - **«Перестроить цикл»** — отдельный полный предпросмотр старых и новых дат, учёт согласованности, явное подтверждение и сохранение как новой редакции/версии, не тихое изменение.
5. После изменения **название/опорные даты карточки** не должны вводить в заблуждение: либо текущие опорные ДП корректно пересчитываются как метаданные с устойчивым `cycle_id`, либо карточка показывает исходные опоры и **отдельно фактические скорректированные ДП** с понятной подписью; нельзя сохранять старый заголовок как будто дата не менялась (дефект #28).
6. **Уже сохранённые планы сотрудников не переписывать молча.** Показывать предупреждение о затронутых записях и создавать/предлагать отдельную новую редакцию для пересчёта, с сохранением истории; пользователь контролирует когда применить изменения. Предпросмотр — без записи.
7. Отмена без сохранения оставляет старую дату, парность, расписания сотрудников и цикл неизменными. Все подтверждённые изменения переживают перезапуск; ведётся запись в журнале и резервная копия.

### Минимальный UX без перегрузки

Кнопки на карточке цикла: **«Создать виды графиков»** (если они ещё не создавались), **«Показать виды графиков»** (если готовы), **«Изменить рейс»** у конкретной даты. Самая важная кнопка при первом построении: **«Сохранить цикл и два графика»**. Не показывать новичку поля `cycle_id`, `sequence`, `pair_id`, версии и технические слова; эти связи автоматические.

**Тесты:** на синтетических двух сургутских циклах проверить создание двух пар в одном действии, отсутствие смешивания ДП при Конструкторе, редактирование не-опорной и опорной ДП, отказ от дубля/конфликта в одном цикле, отсутствие изменений чужого цикла, влияние на уже записанные планы, отмену, сохранность после перезапуска, журнал/rollback, редактирование текста инструкции. Все новые UI/серверные функции здесь — **требования и дизайн**, ещё **не реализованы и не проходили CI/ALT-проверку**.
