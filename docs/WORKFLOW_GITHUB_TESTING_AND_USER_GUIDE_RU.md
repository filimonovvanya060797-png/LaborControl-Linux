# LaborControl R11 → ALT Linux — порядок совместной работы и ведения GitHub

**Согласовано:** 21 ноября 2026 г.; актуализировано 24 ноября 2026 г.  
**Назначение:** постоянные правила для следующего чата, любого разработчика и дальнейших проверок LaborControl.  
**Приоритет:** актуальное прямое решение пользователя важнее прежнего плана. Этот документ описывает договорённый способ работы; он не утверждает, что все функции R11 уже проверены.

## 1. Кто чем управляет

**Пользователь — руководитель функционального тестирования.** Он выбирает, **какой раздел, инструмент и конкретную операцию** проверять следующей, показывает фактическую работу на ALT Linux, определяет правильный рабочий сценарий техника и согласует итоговые тексты инструкций. Ассистент **не начинает другой ручной функциональный тест без выбора пользователя** и не перескакивает по разделам.

**Ассистент — техническая поддержка разработки, проверки и документации.** Для выбранной операции он самостоятельно изучает исходники через GitHub, уточняет крайние случаи, ищет возможные ошибки, готовит синтетические тестовые данные, запускает доступные автоматические тесты, сопоставляет ожидаемое поведение с реализованным, оформляет баги, готовит безопасные исправления в отдельных ветках, проверяет CI и ведёт документацию.

**Пользователя не привлекают к техническим действиям, которые ассистент в состоянии выполнить сам.** Не запрашивать рутинные `cmp`, хэши, просмотр кода, CI и подобное, если их можно проверить через GitHub. Пользователь нужен там, где требуется его конкретная ALT Linux VM, реальный интерфейс или решение о правильной бизнес-логике. У ассистента **нет автоматического доступа к пользовательскому рабочему столу**: не утверждать, что физически проверено на ALT Linux, если это только GitHub Ubuntu CI.

## 2. Одна функция — один законченный цикл

1. Пользователь называет функцию/операцию, которую сейчас тестируем.
2. Ассистент определяет точный критерий успеха, по возможности сверяет с кодом, дополняет сценарий пограничными случаями и готовит необходимые тестовые файлы.
3. Пользователь выполняет выбранный сценарий в **изолированной тестовой** настольной программе; присылает скриншоты и наблюдения. Ассистент сверяет их с ожидаемым результатом. Не выдавать предполагаемый результат за увиденный.
4. Если найдена ошибка, ассистент добавляет её с критерием приёмки в единый накопительный журнал текущей сборки. **Самостоятельно исправлять сразу только по решению пользователя**; отложенные замечания записывать в тот же журнал и возвращаться к основной проверке. Отдельный Issue только для крупной самостоятельной задачи.
5. При согласованном исправлении: отдельная ветка, минимальное изменение кода, автоматический регрессионный тест, GitHub Actions, draft PR; никакие изменения не считаются установленными на ALT Linux до отдельного обновления.
6. Отдельно фиксируются результат теста и доказательство; только после подтверждённого поведения создаётся/обновляется глава пользовательской инструкции.
7. Пользователь проверяет понятность текста и согласует главу. Следующую функцию **выбирает пользователь**.

**Завершение:** в конце **каждой завершённой проверки** писать отдельной строкой **«Проверка закончена.»**, рядом явно указывать результат: `PASS_ALT`, `FAIL`, `BLOCKED`, `PARTIAL`, иной статус. Не объявлять завершённым тест, ожидающий дополнительных скриншотов/действий; для него писать «Проверка продолжается» и что осталось. Длительную работу сопровождать краткими промежуточными результатами, а не молчанием.

## 3. Разделение трёх документов

| Материал | Назначение | Где хранить |
|---|---|---|
| **Руководство пользователя** | Чистовые понятные пошаговые инструкции без «мы тестировали», ID теста и технических отладочных пояснений | Черновики, фотографии и готовые главы в ChatGPT Library `/LaborControl R11/Инструкция/`; одобренная версия может быть включена в GitHub и в раздел «Инструкция» приложения |
| **Протокол тестирования** | ID теста, сборка/commit, входные данные, ожидание, наблюдение, снимки, статус, отметки о проверках | `docs/R11_FULL_TEST_CYCLE.md` как матрица плана; актуальные протоколы/отчёты в репозитории GitHub или в закрытой библиотеке для скриншотов |
| **Реестр ошибок** | Что сломано, шаги воспроизведения, ожидаемое/фактическое, приоритет, статус, исправление и повторная проверка | Единый накопительный Issue текущей сборки; отдельные крупные задачи связаны ссылками; изменение кода — отдельный Pull Request |

Не смешивать **тестовую историю** с текстом, который увидит обычный техник. Черновик руководства — не доказательство прохождения теста.

## 4. Как писать руководство — простой язык и реальные скриншоты

Главная цель: новый сотрудник садится за компьютер, открывает главу, находит кнопку на иллюстрации, выполняет действие и понимает результат **без помощи опытного техника**.

- Писать обычными словами: **«Нажмите „Выбрать файл“», «Укажите таблицу», «Нажмите „Проверить файл“», «Проверьте ФИО и номера»**, не «выполните маппинг полей».
- **Разрешено объединять несколько нажатий в один шаг**, если они находятся на одном экране и последовательность однозначна. Не дробить искусственно. Разделять, когда меняется окно или есть риск ошибки/потери данных.
- На изображении ставить **аккуратные метки 1, 2, 3**, стрелки, рамки и при необходимости короткие подписи; в тексте расшифровывать те же номера и порядок. Использовать единый стиль для всех глав.
- **Пользователь присылает чистые скриншоты, по возможности без стрелок. Ассистент сам делает стрелки, нумерацию и оформление**; ранее присланные изображения с красными стрелками можно переоформить при наличии чистой версии.
- Описывать **зачем** нажимать, **что появится** и **как понять, что всё сделано верно**. Для опасных действий добавлять предупреждение.
- Инструкция включает назначение раздела, подготовку, пошаговые операции, описание всех видимых кнопок и полей, результат, частые ошибки и безопасное исправление.
- **Чистовую главу выпускать только после успешной проверки функции и одобрения пользователем.** Пока проблема не исправлена — черновик/открытое замечание. Скриншоты со старым интерфейсом после UI-исправлений заменять.
- Исходные снимки хранить без потери качества; не уничтожать оригинал при нанесении меток.

## 6. Автоматические проверки (ассистент выполняет по возможности самостоятельно)

- Go: `go test -count=1 ./...`, `go vet ./...`, `go test -race -count=1 ./...`.
- Linux-сборка контроллера, сборка GTK/WebKit, изолированный запуск процесса с синтетической БД, проверка сохранения после рестарта.
- JavaScript: синтаксис и ESLint `no-undef` для обоих реальных HTML-интерфейсов; smoke-тесты экранов в Node VM и в настоящем WebKitGTK под Xvfb.
- Для каждого исправленного бага — **автоматическая негативная или регрессионная проверка**, желательно доказывающая неизменность БД при ошибке.
- Для расчётов требуются одинаковые **обезличенные входные данные и эталон Windows R11**. Зелёный CI и наличие кнопок не доказывают бизнес-эквивалентность.
- Для Excel-«разукрашки» отдельно сравнивать результат Linux с действующим Windows Excel-инструментом, а не считать вкладку «Разукрашка / события» полной заменой.

**Статусы результатов:** `NOT_RUN`, `IN_PROGRESS`, `PASS_UBUNTU`, `PASS_ALT`, `MATCH_WINDOWS`, `FAIL`, `BLOCKED`, `PARTIAL`, `N/A` (с обоснованием). Для ручных тестов указывать, что именно видно; если подтверждена только часть списка, не ставить `PASS_ALT` всему импорту.

## 7. Скриншоты, файлы, безопасность и хранение

- У пользователя ALT Linux Workstation K 11.4 в VirtualBox, отдельная экспериментальная настольная программа и отдельная тестовая база. **Рабочую базу Windows и реальные табели/ИСАТ/SAP нельзя использовать для испытаний**.
- Для тестов создавать вымышленные ФИО, номера, циклы и выгрузки. Даже в приватный GitHub **не загружать реальную личную информацию, реальные базы или скриншоты с такими сведениями**. Если для воспроизведения нужна реальная структура — обезличить или согласовать безопасный способ.
- **Скриншоты пользователя для инструкции сохранять в ChatGPT Library** в тематической папке (например, `/LaborControl R11/Инструкция/Сотрудники/EMP-IMPORT-01/`). В GitHub хранить тестовые инструкции, безопасные синтетические материалы и при необходимости одобренные обезличенные изображения.
- Пользователю предоставлять исходные тестовые CSV/XLSX и документы с прямыми ссылками; не просить его вручную создавать 15 строк, если это может подготовить ассистент.
- Перед обновлением/экспериментами с данными нужна проверенная резервная копия. Изменение в репозитории **не устанавливает** новую версию в VM автоматически. После обновления повторно проверить затронутую функцию и сохранность данных.

## 9. Как продолжать в новом чате

1. Сначала открыть **актуальный единый журнал сборки** (на 24.11.2026 — #47), прочитать **этот документ**, `docs/R11_DEEP_AUDIT_20261121.md` и актуальный план `docs/R11_FULL_TEST_CYCLE.md` из ветки документации; **сверить текущие PR, Issues, рабочую ветку и CI** в GitHub, поскольку этот файл — снимок на указанную дату.
2. Кратко назвать последний подтверждённый результат и незавершённый пункт. Не повторять успешно пройденные действия без причины.
3. **Спросить, какой тест пользователь выбирает дальше, если он ещё не выбрал.** Если уже выбрал — работать только по нему.
4. При ответах разграничивать «проверено ассистентом в CI», «показано на скриншоте пользователя на ALT Linux» и «совпало с Windows R11».
5. В конце каждой **законченной** проверки однозначно написать **«Проверка закончена.»**; если она продолжается — указать причину и следующий конкретный шаг.
