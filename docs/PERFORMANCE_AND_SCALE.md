# LaborControl R11 — масштабирование и производительность

**Дата:** 20.11.2026  
**Статус:** проектные требования и план испытаний; часть параметров требует подтверждения пользователя.

## 1. Подтверждённый масштаб

Пользователь подтвердил сценарий: **один техник на одном компьютере ведёт около 450 сотрудников**. Это основной целевой режим первой версии Linux-порта.

Для текущего этапа не требуется общая база нескольких техников. Возможное расширение на несколько рабочих мест в будущем не считается текущим требованием и не должно усложнять первую реализацию без необходимости.

Пока НЕ подтверждены:
- глубина истории, которую нужно хранить и быстро просматривать (годы);
- типичные и максимальные размеры выгрузок ИСАТ/SAP;
- конфигурация CPU/RAM/диска рабочей станции и VM.

Не считать эти неизвестные требованиями по умолчанию; уточнить до окончательного выбора архитектуры и числовых SLA.

## 2. Что означает 450 сотрудников в данных

При ежедневном учёте один год содержит примерно 450 × 365 = **164 250 записей сотрудник-день**. За пять лет — около **821 250** таких записей, без учёта полётов, событий, отпусков, РВД, импорта и журнала. Это не чрезмерный объём для правильно спроектированной локальной БД, но он уже требует отказа от подхода «при каждом действии перечитать и переписать всё хранилище».

Само число сотрудников не является главным риском. Важнее:
- сколько лет истории хранится;
- сколько записей факта/полётов/событий приходится на сотрудника;
- насколько часто выполняются массовые пересчёты и импорты;
- сколько параллельных операций выполняет приложение (даже при одном пользователе).

## 3. Наблюдения по текущему прототипу

Текущая папка `port/controller` — перенос контроллера R9/preview, а не готовый Core R11. В имеющемся коде:
- основные коллекции сотрудников, дней, РВД, событий, полётов, заметок и журнала загружаются из `labor_control.json` как JSON-массивы;
- `loadMainDB` читает и разбирает весь JSON-файл;
- `saveMainDB` сериализует коллекции и записывает весь JSON-файл целиком (с резервной копией);
- для расчётов создаются временные map-индексы, например по сотруднику и дате;
- Табель 2.0 использует отдельный JSON `labor_control_tab2.json`;
- документация описывает обновление состояния раздела Табеля 2.0 опросом файла каждые 5 секунд.

Такой формат полезен для совместимости и раннего прототипа, но его нельзя без нагрузочных испытаний принимать как окончательное хранилище для многолетней истории и массовых операций. Успешные текущие `go test`, `go vet` и `go build` не измеряют производительность и не подтверждают масштаб 450 сотрудников.

## 4. Предлагаемые архитектурные правила

1. **Сначала модель данных и контракты R11.** Не менять бизнес-правила ради ускорения; вычисления должны давать тот же результат, что и эталон R11.
2. **Хранилище с транзакциями и индексами.** Для подтверждённого режима «один техник — один компьютер — около 450 сотрудников» принять SQLite как основной кандидат и целевое локальное хранилище. Она не требует отдельного сервера, поддерживает транзакции и индексы и подходит для такого объёма при корректной схеме. Окончательное внедрение — после инвентаризации Core, проверки совместимости Go-драйвера и тестовой миграции. Базу хранить на локальном диске, не в общей папке/сетевом ресурсе. PostgreSQL сейчас не требуется; вернуться к оценке серверной БД только если появится подтверждённая потребность в общей базе нескольких рабочих мест.
3. **Индексы по реальным запросам.** Как минимум оценить уникальность табельного номера; составные индексы по `(employee_id, date)`; поиск по табельному номеру/дате; даты полётов; тип/период событий и РВД. Окончательный набор подтвердить профилем запросов и планом выполнения.
4. **Не загружать и не отображать всё без необходимости.** Выбирать данные по сотруднику, месяцу и периоду; использовать пагинацию/виртуализацию больших таблиц, если измерения UI покажут необходимость.
5. **Массовые операции — пакетно и атомарно.** Импорт сначала попадает во временную область, проходит проверку и предварительный просмотр, затем применяется одной транзакцией. Повторный импорт должен иметь определённые правила идемпотентности и обнаружения дублей.
6. **Тяжёлые операции не блокируют интерфейс.** Импорт, массовое построение графиков и большие отчёты выполнять в фоновых задачах с прогрессом, отменой там, где это безопасно, и понятным журналом.
7. **Кэшировать только производные данные.** Результаты расчётов привязывать к версии исходных данных и инвалидировать при изменениях. Кэш не должен становиться источником истины.
8. **Журнал и резервные копии.** История изменений должна быть надёжной и доступной для аудита; резервное копирование и восстановление проверяются на больших тестовых базах.
9. **Сохранить совместимость.** Миграция JSON → новое хранилище (если будет выбрана) должна иметь проверку полноты, обратимое резервное копирование и тесты round-trip на обезличенных копиях. Оригинальные базы не изменять экспериментами.

## 5. План нагрузочных испытаний

Использовать только синтетические данные или обезличенные копии. Никаких реальных персональных данных в GitHub Actions и тестовых отчётах.

Минимальные профили:
- **Базовый:** 450 активных сотрудников, текущий месяц, полный набор плановых ячеек и типовых событий.
- **История:** 450 сотрудников × 5 лет ежедневных записей (ориентир ~821 тыс. строк сотрудник-день), плюс синтетические полёты, события, РВД и журнал.
- **Пиковый импорт:** крупные файлы ИСАТ/SAP; точный размер определить по реальным типовым обезличенным выгрузкам.
- **Массовые операции:** построение/пересчёт графика для всех 450 сотрудников, массовое изменение, импорт и сверка Табеля 2.0.
- **Параллельные операции одного приложения:** проверить, что фоновые импорты/пересчёты и запросы UI не приводят к блокировкам, потерянным обновлениям или чтению частично сохранённых данных. Тест общей базы нескольких техников в текущий объём не входит.

Для каждого профиля измерять время ответа (p50/p95), полное время операции, CPU, RAM, объём БД, число прочитанных/записанных строк и блокировки. Сохранять результаты как базовую линию, сравнивать после изменений.

## 6. Правильность важнее ускорения

Нагрузочный тест считается успешным только вместе с проверками целостности:
- один и тот же набор исходных данных даёт одинаковые результаты расчётов;
- нет потерянных/дублированных часов, смен, полётов и событий;
- массовый импорт либо применён целиком, либо не применён вовсе;
- повторная загрузка не создаёт дубликаты сверх согласованных правил;
- параллельные операции одного приложения не приводят к потерянным изменениям или чтению частично записанных данных;
- после перезапуска и восстановления резервной копии данные и контрольные суммы/итоги совпадают;
- результаты критических сценариев сверены с эталоном Windows R11 на обезличенных данных.

## 7. Критерий готовности

Нельзя объявлять производительность подтверждённой только по успешной компиляции. Отдельно должны быть пройдены:
1. функциональная матрица R11;
2. нагрузочные профили 450 сотрудников и многолетней истории;
3. тесты целостности и восстановления;
4. повторные измерения на зафиксированной конфигурации ALT Linux/VirtualBox.

Числовые SLA по скорости устанавливаются после уточнения оборудования и глубины истории и после первого измерения на ALT VM. Текущий целевой режим — один техник на одном компьютере.
