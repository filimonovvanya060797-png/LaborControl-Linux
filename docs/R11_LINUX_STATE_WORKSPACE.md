# LaborControl R11 — локальный Linux state workspace

**Статус:** первый изолированный рабочий модуль; не полноценный Core R11.  
**Цель:** дать Linux-порту безопасное локальное хранилище состояния в подтверждённой форме Windows R11 и базовое редактирование плановых дней до восстановления алгоритмов Core.

## Запуск

Если Linux-контроллер не находит рядом бинарник `LaborControl_Core`, он на ALT Linux может запустить автономный локальный режим и открыть:

- UI: `http://127.0.0.1:8779/r11`
- API состояния: `GET http://127.0.0.1:8779/api/state`

На Windows поведение не меняется: автономный режим отключён, штатный Core остаётся обязательным.

Локальный режим явно помечен версией `R11-LINUX-STATE-COMPAT/0.1`. Это не запуск и не эмуляция полного Windows Core R11.

## Хранение

Файл базы: `labor_control.json` в локальном каталоге приложения:

- Linux: `$XDG_DATA_HOME/LaborControl`, либо `~/.local/share/LaborControl`;
- Windows-путь здесь не используется.

Файл содержит объект `data` без API-обёртки. Неизвестные ключи корня, данных и существующих записей дней сохраняются при изменении.

Если файла ещё нет, GET возвращает пустое состояние в памяти и **не создаёт файл**. Первая запись создаёт базу.

## API

### GET /api/state

Возвращает форму конверта, обнаруженную в Windows R11:

- `data` — объект с 18 полями состояния;
- `data_path` — локальное имя файла без абсолютного пути;
- `discrepancies` — пустой массив (расчёт расхождений пока не реализован);
- `version` — `R11-LINUX-STATE-COMPAT/0.1`.

Если локальная база отсутствует, все коллекции инициализируются пустыми массивами, `next_id=1`, `schema_version=0`.

### POST /api/state/import

Принимает либо Windows-ответ `/api/state` с объектом `data`, либо сам объект `data`. Проверяет наличие 18 ключей и соответствие известным типам. Неизвестные поля сохраняются. Если локальная база уже существует, перед заменой создаётся резервная копия в `backups/`.

Импорт выполняется в локальный loopback-сервер. UI читает выбранный файл браузером и отправляет его только на `127.0.0.1`. Не добавлять реальные файлы состояния в GitHub и не отправлять их в чат.

### POST /api/state/days

Пакетное изменение плановых дней:

```json
{
  "days": [
    {
      "employee_id": 1,
      "date": "2026-01-01",
      "plan": "11",
      "plan_hours": 11
    }
  ]
}
```

- до 10 000 изменений в одном пакете;
- обязательны существующий `employee_id`, дата `YYYY-MM-DD`, явные `plan` и `plan_hours`;
- плановые часы ограничены диапазоном 0–24 как базовая защита от ошибочного ввода, но это **не полная валидация бизнес-правил R11**;
- дубли дней в одном пакете и дубли ключа сотрудник/дата в базе отклоняются;
- обновление существующего дня меняет только `plan`, `plan_hours` и переданный optional `state`; факт, часы факта, смена, комментарий и неизвестные поля остаются прежними;
- новый день получает новый `id`, пустые поля факта/смены/комментария и увеличивает `next_id`;
- один журнал операции добавляется на весь пакет;
- перед сохранением создаётся одна резервная копия, затем выполняется атомарная запись.

## UI

- просмотр месяца в таблице;
- поиск по табельному номеру и ФИО;
- страницы по 40 сотрудников, чтобы не рендерить сразу все 450 строк;
- редактирование обозначения плана и плановых часов;
- пакетное сохранение с одной резервной копией;
- локальный импорт JSON-состояния Windows R11.

## Что ещё НЕ реализовано

Этот модуль не содержит:

- алгоритма АвтоГрафа и построения/пересчёта циклов;
- бизнес-правил полётов, рейсов, ДП и привязок;
- официальных редакций и версий графиков;
- правил отпусков, больничных, командировок и сверки событий;
- расчёта `discrepancies`;
- полного набора CRUD-операций Windows Core R11;
- подтверждённой эквивалентности форматов и поведения на реальной рабочей базе.

Поэтому UI прямо предупреждает, что это локальный редактор плановых дней, а не полноценный Core R11. Нельзя использовать его для производственного закрытия табелей до завершения функциональной сверки.

## Тестирование

Синтетические тесты покрывают пустой GET без создания файла, импорт Windows envelope, проверку схемы, пакетное создание/обновление дней, резервную копию, журнал, сохранение факта и неизвестных полей, а также отклонение некорректного пакета без изменения базы.

Отдельная нагрузочная проверка на 450 сотрудников и многолетней истории ещё не выполнена.
